# Product Stack Bakeoff — Phase A / 产品栈对比 — Phase A

Date / 日期: 2026-07-13

## 产品导向转型 / Product-oriented pivot

OpenLocus-Lab 现在是选择未来产品默认算法栈、可选层级、回退策略、支持语言/仓库规模、资源 envelope 与稳定集成契约的实验对比场地。近期不做模型训练。未来生产实现将在实验室产出落地规范后放入独立的目录/仓库。

对比通过规范化候选与上下文包 schema 进行，而非整 agent 对比。历史实验室工作保留；不会因对比失利而删除路线。

## Phase A 交付物 / Phase A deliverable

Phase A 是 *规范化对比表面*，不是经验锦标赛。它定义并校验（契约版本 `product_bakeoff_contract.v12`）：

- 公开 `BakeoffTask`（含扩展任务族：ambiguous_target、error_text、configuration_discovery、test_discovery、no_answer）与仅评分方 `TaskOracle` 分离（关联 `OracleSupportRecord` 含 support span + relation + target reference；严格 deterministic-oracle 要求：deterministic 精确 1 span、multi_target >= 2、abstain/stress 为 0；v4 闭合：distinct canonical span、positive/negative 不相交、拒绝重复 negative、每个 support target 精确在 acceptable target 集合中、拒绝重复 support、严格 kind 基数；v4 删除 gold 便捷别名 — 规范表示仅为 `acceptable_target_spans`）；
- 规范化 `AdapterRequest` / `BakeoffRunSpec` 冻结对比单元，含实际逐文件冻结 manifest/source-visibility/visible-tree digest、闭合 cold/warm 缓存状态、交叉校验的 task/interaction/operation 字段、单独声明且绑定到实际可写状态根路径的 writable-state-root id，`fairness_fingerprint` 源自除适配器身份与已测资源外的所有公平相关字段；
- 规范化 `Candidate`（path、range、有限适配器本地越高越好 score、reason、channels 为描述符声明输出 channel 子集、adapter provenance 须匹配描述符身份）— 单一候选集合；候选不能提供 excerpt/hash/freshness/verified；
- 当前源 `BakeoffVerifiedEvidence` 仅由公共 harness materializer 从单次源字节读取构造 — **仅 bakeoff schema**（非生产 EvidenceCore）：明确 `source_sha256`（全文件 SHA-256）、`excerpt_sha256`（excerpt SHA-256）、tuple `why: tuple[str, ...]`、实际选中源 excerpt 与 freshness 元数据。精确生产 EvidenceCore 投影（`content_sha` BLAKE3、`why[]` 列表、生产 channel）**延迟至落地集成**；bakeoff 结果**不能直接作为生产 EvidenceCore 传递**。不添加 BLAKE3 依赖；
- 不可信 `BindingProposal`（仅候选引用/角色）作为策略拥有的包组装边界，使 S0-S5 包策略可不同而公共 materialization/rendering 固定。v6：proposal 携带闭合 `proposed_status`（`ready` / `uncertain` / `no_evidence`）加 `status_reason`；强制精确组合（ready 需 refs 且无 reason；uncertain 需 reason；no_evidence 需 reason、无 refs 且仅在无 evidence 时有效）；ok 结果须携带显式 proposal；harness 从 proposal 与实际 evidence 派生最终 pack；v8：每个 `status=ok` 结果**必须**携带显式 `BindingProposal`（在 `validate_adapter_result` 候选校验成功前强制 — 不存在 "proposal, if present" 路径），包括零候选/evidence 结果，须显式 propose `no_evidence` 且含非空已校验 reason 与无 refs；`build_context_pack` 在 evidence 分支前要求 proposal 作为纵深防御；
- `ContextPack` 含 targets、support、uncertainty/status、diagnostics、实际渲染上下文与 harness 重算的精确预算用量（ceil 估算器 v4，基于实际渲染上下文）。v6：pack 校验消费**实际 bakeoff evidence tuple**，确定性校验每个 target/support path+range 等于其引用 evidence、精确重渲染上下文、与每个 `BudgetUsage` 字段（含 caller 提供的 candidate count 与累计 episode 字段）；外部伪造字段无法通过；
- `AdapterHooks`（可选 prepare/index hook + 必需 query hook；均为顶层函数以支持 Windows spawn picklability）与 `AdapterDescriptor` 含支持语言、persistent-state behaviour（cold/warm reuse 语义）、执行模式、上游修订、SPDX/license 状态与描述符声明输出 channel；v6：`fallback_chain` 完全**移除**（per-result `FallbackRecord` 为唯一回退契约）；harness 拥有阶段计时（setup/index/query/materialize/render）；`validate_descriptor_hooks`（v4）交叉校验描述符与 hook：lifecycle hook 须有 `prepare_index` 能力、`warm_reuse` 须有真实 state-building hook（prepare 或 index）、`cold_rebuild` 须有 index、hook 缺席不能声称 `prepare_index` 为默认可执行能力；v7：`execution_mode` 收窄为唯一真实值 `process_isolated` — harness 为每个 attempted prepare/index/query hook 生成新的 `multiprocessing.spawn` 子进程（跳过的 warm hook 不生成子进程），每个阶段独立使用现有冻结 `timeout_seconds` 并在超时时即时 terminate/kill/reap，仅异常 TYPE（非 message）跨进程边界传递，生命周期状态仅通过声明的 `writable_state_root` 共享，这是进程隔离 + 超时强制，**非 OS 安全沙箱**；拒绝 `in_process` / `subprocess` 词汇漂移；v8：stage 传入子 worker 并强制**精确 hook 返回** — prepare/index 必须返回恰好 `None`、query 必须返回恰好 `AdapterResult`，其余任何形状（含 query 返回 `None` 或 prepare/index 返回 `AdapterResult`）为 `malformed/non_adapter_result`；spawned 进程清理在所有路径上确定性进行（`proc.start()` 在清理保护边界内；child/parent pipe 端点在所有路径关闭；跟踪 `started`；每个已启动子进程按需即时 terminate、无条件 join（即使已退出）、必要时 kill+join、仅在不活跃后 `proc.close()`；避免 double-close 异常）；真实 multiprocessing 启动/资源/通信失败在清理后**抛出专用 `HarnessInfrastructureError`** 中止整个 bakeoff — 永不被 `run_adapter` 的适配器错误捕获捕获，永不转换为某适配器的 `ValidatedRunRecord` 或对比数据点（进程已启动时的正常子进程 EOF/进程死亡仍为闭合 stage 错误）；
- `ResourceSample`（harness 测量；保留在 validated 私有记录中；拒绝适配器 authored 测量；不可用阶段显式为 None；非负有限校验；aggregate 计数源自实际 sample）与 `AdapterResult` 含单一候选集合、精确能力账本（键须精确等于描述符能力；公共 harness 能力不是适配器账本条目）、结构化 unavailable->executed 回退溯源与闭合状态词汇。v6：适配器能力集为 `prepare_index` / `candidate_search` / `target_binding` / `support_expansion` / `two_step_support`；`validate_capability_ledger_honesty` 交叉校验账本与实际执行（prepare/index 是否 attempted、target/support refs 是否存在、support 操作是否产生 support）及反向；cold 生命周期执行为 `executed`、warm reuse 跳过为 `legitimate_skip`、两步 support 不能在 support 操作产生 support 时称 `unsupported`；`FallbackRecord` 校验引用 cap 已声明、unavailable->executed/none、无重复 unavailable capability、每个回退的 unavailable capability 恰一条记录；
- 使用合成临时仓库的 conformance runner，非空覆盖全部九个 conformance 类别，采用阶段感知的进程隔离强制超时（v7：每个 attempted prepare/index/query hook 生成新的 `multiprocessing.spawn` 子进程；每个阶段独立使用现有冻结 `timeout_seconds` 即时终止 — 无宽限期 — 仅 join 回收；仅异常 TYPE，非 message）、COMMON 安全路径策略（`_validate_safe_path_under_root`：词法相对路径 + resolved confinement + ORIGINAL LEXICAL 全组件 symlink 检查；拒绝父 symlink 与 symlinked 路径组件，包括目标仍在 root 内的 in-root 父 symlink；out-of-root writable-state 在创建前被拒绝；v5：writable-state root 等于源 root、为任何 visible path 的祖先/相等、或包含任何 visible path 时在 `mkdir` 前被拒绝）、prepare 后/index 后/query 后中间不可变源扫描（使 mutate->restore 无法通过）加每个退出路径最终扫描、执行根绑定（resolved 执行根等于 snapshot root）、适配器 id/version/language 绑定、稳定 target ID 用于两步 lineage、完整 Cartesian comparison-matrix 校验器（adapter x logical-cell x repetition x cache x step）含 FULL 语义 envelope 确定性（record/result/pack status、canonical failure category、capability ledger，然后 accepted group 的 hash；accepted->rejected->accepted 对抗用例）、fail-closed `validate_run_record` 用于 comparison 与 aggregation（拒绝适配器异常 MESSAGE 文本与原始适配器 authored failure category；仅用 stage + exception TYPE 映射到 canonical harness category）、`capability_ledger_entry_count` aggregate scalar 对账 `sum(capability_status_counts)`（同一 accepted+validation-rejected 非私有记录；tampered-bucket 与 tampered-scalar 对抗用例被拒绝）与真正闭合/精确/无异常的报告 schema。v6：对抗性伪造 pack 字段（伪造 target/support path+range、同长度伪造 render、每个 `BudgetUsage` 维度与累计字段）与能力矛盾（每个 oracle 发现的矛盾）由直接探针拒绝。v7：`BudgetUsage.over_cap`/`over_cap_reason` 完全移除（cap 强制仅在 `validate_against`；over-cap 结果为 rejected 记录，非 pack 标志）。

## 公平契约 / Fairness contract

可比 arm 须在 fairness fingerprint 上精确匹配：schema/run-cell/task/snapshot/source-visibility ID 与实际 digest、query、语言/任务族、适配器重复、闭合 cold/warm 缓存状态、交互模式与 lineage、candidate/evidence/target/support/rendered-context/episode/step 上限、超时、renderer/materializer/budget-estimator 版本与可写状态根 id。适配器身份与已测资源排除。run spec 绑定到实际冻结 snapshot digest；不匹配则拒绝。完整 Cartesian comparison-matrix 校验器强制 adapter x logical-cell x repetition x cache x interaction-step 完整性、拒绝缺失/意外/重复键、在精确 logical cell 内比较 fingerprint、用 reps 1/2/3 验证 FULL 语义 envelope 确定性（record/result/pack status、canonical failure category、capability ledger，然后 accepted group 的 hash；canonical hash 排除重复身份）。accepted->rejected->accepted 对抗记录用例证明中间重复被拒绝时检测为语义 envelope 漂移。

## 两步交互 / Two-step interaction

最小交互支持已冻结：`interaction_mode = one_shot | two_step`，`operation = context | support`；通过 `episode_id`、`request_id`、`parent_result_id`、`bound_target_id` 的 episode/request lineage。非空执行了一个真实合成 context->support episode，含注册父/目标（通过 `stable_target_id` 从实际 materialized target 派生稳定 id）、不变 lineage（实际 target、task、episode、snapshot/visibility/renderer/materializer/estimator 身份、不变 episode caps、parent step）、实际累计 episode 预算核算，以及对抗性 unknown-parent / unknown-target / cross-task / cross-episode / cross-snapshot / altered-cap / repeated-step / budget-overrun 场景。注册表保持两记录 context->support 范围，非通用工作流引擎。Outcome/patch schema 仍延迟。

## 适配器生命周期 / Adapter lifecycle

最小生命周期契约：可选 `prepare` 和 `index` hook、必需 `query` hook、harness 拥有的阶段计时（setup/index/query/materialize/render）、声明的 persistent-state behaviour（`stateless` / `cold_rebuild` / `warm_reuse`）与显式 cold/warm reuse 语义。在 `warm` cache_state + `warm_reuse` 下，prepare 和 index 被跳过（状态假定已存在）；在 `cold` 或 `stateless`/`cold_rebuild` 下，prepare 和 index 如存在则被调用。未尝试的阶段在 ResourceSample 中为 `None`。这不是插件框架；公共 harness 完成所有源读取/materialization/rendering，适配器仅通过 query hook 发出不可信候选/binding。

v4 有状态生命周期测试（非空）：cold 向 `writable_state_root` 写入状态 marker；warm 在同一 snapshot/root 上观察 marker 同时跳过 rebuild（证明先前状态实际构建并被复用）；v5：warm-without-state 为显式 REJECTED 结果（stateful query 在 warm marker 缺失时返回 failed 结果；canonical failure category 为 `adapter_exception:FailedResult`；不产生成功 pack）；`stateless` 与 `cold_rebuild` 的 warm 请求实际运行配置 hook（stateless 总是 rebuild；cold_rebuild 总是 rebuild index）。prepare 后/index 后/query 后中间不可变源扫描捕获 mutate->restore 模式（若仅最终扫描则可掩盖 mutation）。

## 公共安全路径策略 / Common safe path policy

一个公共安全路径策略（`_validate_safe_path_under_root`）在任何 snapshot 读取或目录创建前应用，跨 manifest/snapshot/tree/candidate/writable 校验复用。它校验：(1) 词法相对路径（无 NUL、UNC、absolute、drive、traversal、backslash、dot-only）；v5：遍历 ORIGINAL LEXICAL 路径组件（非 resolved parts），使目标仍在 root 内的 in-root 父 symlink 也被拒绝 — `full.resolve()` 会解引用此类 symlink 从而隐藏它；词法路径不在 root 下时在 resolved confinement 检查前被拒绝；(2) resolved 根下所有路径组件检查 symlink（拒绝父 symlink 与 symlinked 路径组件）；(3) resolved confinement（完全 resolved 路径须在 resolved 源根下）。Out-of-root writable-state 根在创建前被拒绝（confinement 在 `mkdir` 前校验）。v5：writable-state root 等于源 root、为任何 visible path 的祖先/相等、或包含任何 visible path 时在 `mkdir` 前被拒绝（覆盖 root 与 root/src 探针）。在支持 symlink 的 CI 上执行 symlinked-parent 逃逸 fixture 与 in-root symlinked-parent fixture（目标仍在 root 内）（Windows 无 symlink 权限可显式跳过；Linux CI 须执行两者）。

## Fail-closed 记录校验 / Fail-closed record validation

`validate_run_record` 为 fail-closed，由 `validate_comparison_matrix` 与 `aggregate_public_report` 共同使用。它拒绝：vocab/type/count/hash/resource/status 不一致；pre-execution resource 存在（prevalidation 拒绝不应携带 `ResourceSample`）；以及 `failure_category` 中的任何不安全字符串。适配器异常 MESSAGE 文本与原始适配器 authored failure category 永不到达公共键；harness 仅用 stage + exception TYPE 映射到 canonical category（`adapter_exception:RuntimeError`、`adapter_exception:PartialResult`、`adapter_exception:FailedResult`、`adapter_timeout`、`non_adapter_result` 等）。未通过 `validate_run_record` 的记录计为 rejected-by-validation 并标记 canonical `record_validation:invalid_record`，永不进入 accepted 表面。v9：rejected 记录必须携带空 `capability_ledger_summary` — 仅 accepted 记录可发布已校验 ledger。公开能力计数（`capability_status_counts` / `capability_ledger_entry_count`）仅源自 accepted 记录并对账。v9：accepted 记录 `candidate_count > 0` 时要求 `capability_ledger_summary["candidate_search"] == "executed"`（记录防御，补充 in-run honesty 校验）。公开报告含 `capability_ledger_entry_count` aggregate scalar = 仅 accepted 记录的 `sum(capability_status_counts)`；`validate_written_report` 强制非负 int + 精确求和相等，tampered-bucket 与 tampered-scalar 对抗用例被拒绝。

## v9 闭合 — 全初始源树冻结、hook 前基础设施扫描、含传输的 deadline、能力账本信任

Phase A v9 闭合三个规范性公平问题，不添加算法、数据集、provider、产品仓库代码、通用 plugin/executor 框架或私有 run：

- **全初始源树冻结：** `materialize_snapshot` 将声明迭代器物化一次（不 `set` 折叠）、要求非空字符串、拒绝重复声明、词法校验每个路径、要求 root 预存在为真实非链接/非 reparse 目录、在创建前校验 writable-state root（严格 in-root confinement、无 symlink/junction/reparse 组件、无与声明文件的重叠）、在 `mkdir` 前用 `os.walk(topdown=True, followlinks=False)` 排序名称且 `onerror` 抛出枚举完整源树（通过 `_enumerate_source_tree` 助手，`materialize_snapshot` 与 `scan_visible_tree` 共用）、要求精确集合相等 声明 == 枚举（任何未声明或缺失源均拒绝）、从此枚举构建 manifest/tree digest（非仅声明重读）、仅在相等后创建 writable-state root 并重新校验身份/confinement/类型。声明保持有意义且永不从文件系统派生/修复。`scan_visible_tree` 调用同一枚举器并比较完整 (path, digest, size) 元组、路径集、逐文件 digest、逐文件 size 与 tree digest；无静默 walk 错误。拒绝 symlink/reparse/特殊文件与每个 traversal/lstat/open/read/stat 错误；字节以 before/after 身份/size 检查哈希。仅精确词法 writable-state-root 子树可被排除（当存在时）；缺失 WSR 不被遍历。
- **hook 前基础设施扫描：** `run_adapter` 在 request/descriptor/lineage 校验后且紧接第一次 attempted prepare/index/query 前运行 `assert_snapshot_unchanged`。若在任一 hook 启动前失败，抛出 `HarnessInfrastructureError`（中止整个 bakeoff — 无 rejected 记录）。这是 spawn 前最后的 harness 操作。hook 启动后检测到的突变仍为适配器拒绝。
- **含传输的 deadline（当前 v12 语义）：** `_execute_stage_isolated` 使用单向 `multiprocessing.Pipe(duplex=False)`、`send_bytes`/有界 `recv_bytes`、闭合严格 JSON envelope、`MAX_STAGE_WIRE_BYTES = 8*1024*1024`，以及从进程启动前开始并覆盖接收、解码、校验与 canonical 重建的绝对 deadline。父进程使用一个 receiver 线程与 one-slot queue，并在每个 payload 处理阶段后重检 deadline。发生 timeout 时，harness terminate/kill/reap 子进程、关闭 pipe、join receiver，并确认子进程与线程均不再存活。子进程 EOF、exit、no-send/send failure、超限或 malformed frame，以及歧义 receive 错误均为 adapter-scoped `process_died` 或 `malformed`；它们不能伪造整个 bakeoff 的 infrastructure abort。仅可证明为父进程本地的 setup/start、poll/handle、cleanup/reap 或 receiver-thread 失败抛出 `HarnessInfrastructureError`。`_reap_process` 尝试全部清理并校验子进程不再存活。保持 spawn-per-stage；无 executor。本条记录当前 v12 contract；v10 的历史行为及其在 v11/v12 中被取代的过程见下文。
- **能力账本信任：** 不添加可伪造的 validated boolean。每个 rejected 记录携带 `capability_ledger_summary={}`；`validate_run_record` 拒绝任何非空 ledger 的 rejected 记录。仅 accepted 记录可发布已校验 ledger。公开能力计数/计数条目仅源自 accepted 记录并对账。排序：`validate_adapter_result`（闭合 shape/bindings/descriptor ledger/candidates/fallback）然后 `validate_capability_ledger_honesty`（紧接，在 materialization 前）然后 hash/materialize/pack/register/copy ledger。`candidate_search` honesty：非空候选要求 `candidate_search=executed`；无反向（executed 可返回零）。accepted + `candidate_count>0` 要求 summary `candidate_search=executed`（记录防御）。
- **Oracle visible_files 预检：** `TaskOracle.validate(visible_files=...)` 校验每个 acceptable target span path、support record support_path + target_path 与 must_not_primary_path 属于冻结可见集。oracle 保持仅评分方（无源读取，run phase 期间永不导入）。

## v10 闭合 — 读取前拒绝特殊文件、分配前强制接收边界、真实 worker 发送失败分类

Phase A v10 闭合 v9 已声称保证中的三个狭窄缺口，不添加算法、数据集、provider、产品仓库代码、通用 plugin/executor 框架或私有 run：

- **读取前拒绝特殊文件：** `_enumerate_source_tree` 在 `read_bytes` 前通过 `os.lstat` 结果上的 `stat.S_ISREG(st_mode)` 拒绝特殊文件（FIFO、socket、device、directory、未知文件类型）— 不打开或不读取条目。读取后，after-lstat 须仍为常规文件且 `(st_dev, st_ino, st_mode, st_size)` 身份相同；任何替换/mode/type/size 变化均拒绝。可用身份字段一致比较（`st_ino` 在某些 Windows 文件系统上可能为 0；两边均为 0，故比较仍成立）。root 与 writable-state-root 现有类型校验在 lstat 错误时 fail closed。当 `os.mkfifo` 可用时执行真实 POSIX FIFO 对抗测试，证明 snapshot 构造在不打开 FIFO 的情况下即时拒绝；在 FIFO 不可用的 Windows 上诚实跳过并测试 mock 的特殊 `st_mode` 路径。
- **分配前强制接收边界：** 父进程接收器调用 `recv_bytes(maxlength=MAX_STAGE_WIRE_BYTES)`，使 wire 边界在完整 payload 分配前强制执行（stdlib 先读取长度头，在分配过大 body 前抛出 `OSError`）。At-bound（恰好 `MAX_STAGE_WIRE_BYTES`）成功；worker 侧 over-bound 仍为小型 malformed envelope。v11：父进程观察到的 over-bound 与歧义接收 `OSError` 分类为 adapter-scoped `malformed`（**非**基础设施失败），因为子进程可诱导它们且 stdlib oversize 条件无法在不解析异常消息文本的情况下可靠区分于真实 pipe `OSError`。FakePipe 测试断言 `maxlength` 确实被传递并验证边界行为（at-bound 成功，over-bound 抛出）。
- **真实 worker 发送失败分类（v10，已被 v11/v12 取代）：** v10 引入专用 `WORKER_TRANSPORT_FAILURE_EXIT_CODE = 73` 与 `transport_failure` envelope status 以将真实 worker 发送失败分类为基础设施失败。v11 **移除**了整个机制（见下方 v11 闭合章节），因为它是可伪造的：适配器可调用 `os._exit(73)` 来 author 一个 infra 中止。v11 将每个子进程 EOF/exit code 分类为 adapter-scoped `process_died`（永不 `HarnessInfrastructureError`）。v12 保留 v11 边界并收窄文档声称：现有 `close_without_send` / `os._exit(...)` 测试是 EOF / no-send 测试（子进程关闭管道或在发送前退出），**非**强制 `conn.send_bytes` 在真实 spawned worker 中抛出的 send-failure 测试。文档不再声称 "真实 send failure 测试"；实际证明的分类为子进程 EOF / no-send => `process_died`。

## v11 闭合 — 从适配器控制的 wire 中消除 pickle；移除可伪造的全 bakeoff 中止信号

Phase A v11 闭合 v10 stage 传输中的两个规范性 RCE/可伪造性缺口，不添加算法、数据集、provider、产品仓库代码、通用 plugin/executor 框架或私有 run：

- **有界严格 JSON 原语 wire（run-phase wire 上无 pickle）：** 子进程仅通过 `json.dumps` + `conn.send_bytes` 序列化闭合 JSON 原语 envelope `{"v": 1, "status": <ok|error|malformed>, "payload": <closed_payload_or_null>, "error": <str_or_null>}`。UTF-8 JSON 字节，紧凑/确定性编码（`sort_keys=True`、`separators=(",", ":")`）。不使用适配器定义的 encoder/default/object_hook/repr/string 转换。编码前，返回的 canonical `AdapterResult` 在 EXACT 类型检查（`type(x) is AdapterResult` 等，非接受可重写行为的子类的 `isinstance`）下规范化为新的 plain builtin `dict`/`list`/`scalar` 树。所有嵌套 `Candidate`/`BindingProposal`/`FallbackRecord`/capability-ledger 值在闭合 schema 下逐字段复制，原语精确类型、有限数字、有界字符串/计数/深度。若不满足精确 canonical dataclass 类型、遇到未知/非原语/mapping 子类/自定义对象、property 访问失败、JSON 编码失败、或规范化 envelope 超过 `MAX_STAGE_WIRE_BYTES`，则拒绝/发送小型 malformed envelope。Lifecycle ok 返回精确 `null`。异常 envelope 仅携带可信 `type(e).__name__`（本身有界/已校验）；适配器异常 MESSAGE 文本永不到达 wire。外层 wire envelope 是精确闭合 JSON 对象，含可信 `v`/`status`/`payload`/`error` 字段；避免歧义的 bool-as-int（使用 `type(x) is int/float/bool` 语义）；所有 float 有限；显式最大深度/计数/字符串长度与现有契约最大值一致。
- **严格父进程解码 + canonical 重建（run-phase 模块中无 `pickle.loads`/`pickle.dumps`/pickle import）：** 父进程用现有硬分配边界（`recv_bytes(maxlength=MAX_STAGE_WIRE_BYTES)`）接收字节，严格 UTF-8 解码（拒绝无效 UTF-8 与嵌入 NUL），然后用 `json.loads` 含 `parse_constant` 拒绝（NaN/Infinity）AND `object_pairs_hook` 在每个 object 层级拒绝重复键。不使用可构造任意类型的 `object_hook`。拒绝：无效 UTF-8、trailing/multiple docs、任意层级重复键、NaN/Infinity、错误原语类型、extra/missing keys、过大 depth/count/string length 与闭合 schema 违规。父进程在可信父代码中逐字段重建精确 canonical dataclass（`AdapterResult`、`Candidate`、`BindingProposal`、`SupportBinding`、`FallbackRecord`），然后运行现有 `validate_adapter_result` 与后续 honesty 校验。Deadline 在接收、解码、闭合 wire 校验与重建后重检。保留 no-oracle import 边界。
- **移除可伪造的全 bakeoff 中止信号：** 删除 `WORKER_TRANSPORT_FAILURE_EXIT_CODE` 常量、专用 exit-code 分类、`transport_failure` envelope/status 与所有声称子进程发送失败为可信基础设施的声明。适配器可调用任何 `os._exit(code)`；每个子进程 EOF/exit code 为 adapter-scoped `process_died`（永不 `HarnessInfrastructureError`）。子进程 `send_bytes` 失败：子进程关闭并以非零退出；父进程看到 EOF/进程死亡并分类 adapter-scoped `process_died`。Hostile/oversize 子进程控制帧或歧义 `recv_bytes(maxlength)` `OSError` 分类为 adapter-scoped `malformed`（子进程可诱导；`OSError` 消息不被解析）。`poll` `OSError` 仍为 infra（父进程本地 pipe 状态失败，可证明区分 — 在任何子进程字节被观察前发生）。仅可证明的父进程本地 setup/start 失败与失败的 cleanup/reap/receiver-thread 终止抛出 `HarnessInfrastructureError`。可归因于父进程运行时的进程句柄检查失败可为 infra。父进程拥有的 queue/thread 创建失败可为 infra。无子进程 authored envelope status 可抛出 `HarnessInfrastructureError`。
- **真实对抗性 self-test：** 含嵌套自定义类 / dataclass 子类 / mapping 子类 / 自定义对象（含 `__reduce__`、`__iter__`、property 或 JSON trick）的 hostile canonical-looking 返回**永不**在父进程中执行代码。使用真实 spawned hostile hook 与子进程工作区外的 marker 证明父进程未执行它；子进程本地的任意适配器代码执行是预期的且被隔离。结果拒绝为 malformed/进程失败。精确 canonical `AdapterResult` 经 JSON round-trip 并保持 accepted。外层与嵌套层重复键拒绝；NaN/Infinity 拒绝；无效 UTF-8/trailing docs/错误 shape/extra/missing keys/错误 bool-int/自定义类型均拒绝。直接 fake-transport 回归测试覆盖 depth/count/string caps（`_MAX_STAGE_DEPTH` / `_MAX_STAGE_LIST_COUNT` / `_MAX_STAGE_STR_LEN`）与 `parse_constant` / `object_pairs_hook` 路径。子进程 hook `os._exit(73)` 与若干任意 code => `process_died`，永不 infra。子进程 EOF / no-send（子进程关闭管道或在发送前退出）=> `process_died`；文档不再声称 "真实 send failure 测试"，因为没有测试强制 `conn.send_bytes` 在真实 spawned worker 中抛出。父进程 setup/start 与未回收 cleanup 仍为 infra。父进程观察到的 over-limit `recv` 与歧义 `recv` `OSError` 为 adapter-scoped（无全 bakeoff 中止）。`maxlength` 确实被传递；at-bound 行为已覆盖。重复 hostile/timeout run 不留活跃子进程/receiver 线程。测试在可行处遍历 `_execute_stage_isolated` / `run_adapter`，而非仅直接解码器验证器。

## v12 闭合 — 收紧 adapter-payload 异常边界；hostile 子进程退出后的全 run 续行

Phase A v12 闭合 v11 stage 传输中的三个狭窄 final-review 缺口，不添加算法、数据集、provider、产品仓库代码、通用 plugin/executor 框架或私有 run：

- **Adapter-scoped 解析器异常边界：** 在 `_wire_decode_envelope` 与 `_receiver` 线程中，每个由接收 JSON 字节引起的已知异常被确定性地转换为 `_WireError` 然后 receiver outcome `malformed` — **永不**传播到 receiver catch-all `pipe_error` -> `HarnessInfrastructureError`。具体转换：无效 UTF-8（`UnicodeDecodeError`）、`json.JSONDecodeError`/`ValueError`（含 Python 3.11+ oversized integer-token limit `sys.get_int_max_str_digits()`）、`RecursionError`（深嵌套超出 C 解析器递归限制）、`OverflowError`（数值溢出）、duplicate-key `object_pairs_hook`、`parse_constant` hook（NaN/Infinity）、`_wire_validate_depth_and_primitives` 中的 depth/count/string 上限、`_wire_validate_envelope` / `_wire_reconstruct_adapter_result` / `_wire_reconstruct_candidate` / `_wire_reconstruct_fallback_record` / `_wire_reconstruct_binding_proposal` 中的 exact-schema/reconstruction 失败，以及重建期间的意外 `TypeError`/`KeyError`/`AttributeError`/`IndexError`。一个闭合的 `_WIRE_CHILD_PARSE_EXCS` 元组被 receiver 中每个 per-call `except` 子句共享。真正父进程本地的 `poll` OSError、queue/thread 创建失败、setup/start 启动失败与未回收 cleanup / receiver 线程泄漏失败**仍为**基础设施中止 — 边界严格围绕 strict decode/parse/validate/reconstruct，**非**所有父进程编程失败。
- **Hostile 子进程退出后的全 run 续行（端到端）：** 真实 spawned hostile hook 调用 `os._exit(73)` 产生一个 REJECTED `ValidatedRunRecord`，含 adapter `adapter_exception:process_died` failure category 与 EMPTY `capability_ledger_summary`（仅 accepted 记录可发布 validated ledger）、无 `pack_status`、无 `canonical_pack_hash`，且 `ResourceSample` 含 `query_seconds`。同一测试进程 / bakeoff 序列中的后续 VALID 适配器 run 执行并被 ACCEPTED，`pack_status="ready"`。无 `HarnessInfrastructureError` 抛出，无子进程/receiver 线程泄漏。这证明全 run 续行，**非**仅直接 `_execute_stage_isolated` 分类 — hostile 子进程退出是一条 rejected 记录，不是 bakeoff 中止。
- **文档诚实：** 每个声称专用 worker transport-failure 信号或 worker-send infra 中止仍存在的过期 v10 声明被移除/取代。v11/v12 真相：子进程 EOF、exit、send 失败或歧义 recv 为 adapter-scoped；仅父进程本地 setup/poll/cleanup/reap/thread 失败中止。文档**不**声称 "真实 send failure 测试"，除非确实强制 `conn.send_bytes` 在真实 spawned worker 中抛出；现有 `close_without_send` / `os._exit` 测试是 EOF / no-send 测试，非 send-failure 测试，措辞相应收窄。Depth / count / string / duplicate-key / nonfinite 声明仅因紧凑直接 fake-transport 回归测试覆盖每一项而保留：深嵌套（RecursionError）、oversized integer（Python 3.11+ int-digit limit，feature-detect）、depth cap（33 > `_MAX_STAGE_DEPTH=32`）、oversized string（`> _MAX_STAGE_STR_LEN`）、oversized list（`> _MAX_STAGE_LIST_COUNT`）、嵌套重复键（`object_pairs_hook`）与 NaN/Infinity（`parse_constant`）均拒绝为 adapter-scoped malformed（**永不** infra）。

所有先前 v9/v10/v11 保证保留：全源树冻结、WSR confinement、pre-hook 扫描、读取前特殊文件拒绝、不可变 post-hook 扫描、显式 proposal、仅 harness `VerifiedEvidence`、pack rerender/recompute、仅 accepted ledger、oracle scorer-only、精确 report/matrix 对账、run-phase wire 上无 pickle、无可伪造的全 bakeoff 中止信号。Phase A 公开状态仍严格为合成适配器 conformance 就绪；无真实公平/产品获胜/默认/运营主张。CI 保持 provider-free drift gate（`--check-drift`）。

## 合成-only Phase A 限制 / Synthetic-only limitations

Phase A 使用合成临时仓库，fixture 值刻意与既往真实值无关。它不 clone 外部项目、不排序真实算法、不改变产品默认、不运行 provider、不声称产品有效性。威胁模型仅防止 scorer/oracle/path/excerpt/freshness 事实意外泄漏到适配器输出；它不防御在主机上扫描的恶意可执行文件。对抗性适配器仅测试契约执行（拒绝错误输出），不测试主机沙箱。超时强制为进程隔离即时终止（无宽限期）。

v6：`BakeoffVerifiedEvidence` 是**仅 bakeoff schema**，**非生产 EvidenceCore**。它使用明确 SHA-256 字段/算法命名（`source_sha256`、`excerpt_sha256`）与 tuple `why: tuple[str, ...]`。精确生产 EvidenceCore 投影（`content_sha` BLAKE3、`why[]` 列表、生产 channel）**延迟至落地集成**；bakeoff 结果**不能直接作为生产 EvidenceCore 传递**。不添加 BLAKE3 依赖。

Phase A 公开状态严格为合成适配器 conformance 就绪。它不声称产品/算法就绪、真实公平、S0-S5 conformance、获胜/默认栈、检索/编码改进、真实仓库鲁棒性、支持语言/规模、外部适配器就绪、生产当前性正确或运营验收。

8. 无静默退化 — 每个能力有闭合状态且精确键相等；unsupported/failed/legitimate_skip 不同；结构化 unavailable->executed 回退溯源；v6：描述符 `fallback_chain` **移除**（per-result `FallbackRecord` 为唯一回退契约；校验声明 cap 成员、unavailable->executed/none、无重复）；失败 default 不能伪装为成功；`validate_descriptor_hooks` 交叉校验描述符与 hook（lifecycle hook 须有 `prepare_index`；`warm_reuse` 须有真实 state-building hook；`cold_rebuild` 须有 index；hook 缺席不能声称 `prepare_index` 为默认可执行能力）；v6：能力为 `prepare_index` / `candidate_search` / `target_binding` / `support_expansion` / `two_step_support`；`validate_capability_ledger_honesty` 交叉校验账本与实际执行（prepare/index 是否 attempted、target/support refs、support 操作是否产生 support）及反向；v6：`execution_mode` 收窄为 `process_isolated`（拒绝词汇漂移）；v7：所有第三方 hook（prepare/index/query）均在每个 attempted 阶段的全新 spawn 子进程中运行，独立超时强制（即时 terminate/kill/reap；仅异常 TYPE，非 message）；生命周期状态仅通过声明的 `writable_state_root`；sleeping prepare/index fixture 证明超时拒绝、子进程在延迟 marker 写入前终止（即时与 guard delay 后均不存在）、可见源未改变、含阶段时长的 ResourceSample；适配器生命周期 hook 用 cold/warm reuse 语义非空执行；v5：warm_reuse warm-without-state 为显式 REJECTED 结果（stateful query 在 warm marker 缺失时返回 failed；canonical failure category 为 `adapter_exception:FailedResult`；无成功 pack）；同一 root 的 cold->warm 成功保留（cold 写 marker、warm 在同一 root 观察）；stateless/cold_rebuild warm 请求实际运行 hook；v8：在进程边界强制**精确 stage 返回矩阵**（prepare/index 返回恰好 `None`；query 返回恰好 `AdapterResult`；其余形状为 `malformed/non_adapter_result`），对抗性 prepare->AdapterResult、index->AdapterResult、query->None 探针被拒绝并含资源计时与无 pack；v8：受控 fake-Process 启动失败单元测试证明两端 pipe 均被清理且抛出 `HarnessInfrastructureError`（中止整个 bakeoff，永不为 `ValidatedRunRecord`），且 `run_adapter` 传播而非转换它；prepare/index 失败产生显式失败记录与部分 ResourceSample；v12：有界严格 JSON transport 将子进程 EOF/exit/no-send/oversize/malformed 与歧义 receive 失败归类为 adapter-scoped process_died 或 malformed，永不作为整个 bakeoff 的基础设施中止；os._exit(73) 经 run_adapter 端到端执行，且后续 valid run 仍成功；仅可证明为父进程本地的 setup/start/poll/handle/cleanup/reap/receiver-thread 失败属于 infrastructure failure；严格解码/解析失败（含深递归与超长整数）均为 adapter-scoped malformed
9. Aggregate-only 报告 — 报告仅由 validated run 构建；fail-closed `validate_run_record` 同时 gate comparison 与 aggregation；适配器异常 MESSAGE 文本与原始适配器 authored failure category 永不到达公共键（仅用 stage + exception TYPE 映射到 canonical harness category）；真正闭合/精确/无异常报告校验（拒绝未知顶层与嵌套字段；所有 count 为非负 int 且拒绝 bool；resource count 由 total 约束；canonical constant surface 为集合相等；精确嵌套键；对账 failure/result/pack/category/privacy/validation 总计；v5：`capability_ledger_entry_count` scalar 对账 `sum(capability_status_counts)`，tampered-bucket 与 tampered-scalar 对抗用例被拒绝；对抗性 negative/string/bool/oversized/truncated/unknown 用例无异常拒绝）；隐私扫描拒绝 identities/queries/paths/excerpts/oracle/workspace/singleton 事实；ResourceSample 保留在私有记录中含诚实 aggregate 计数；CI 重跑 conformance 并比较提交报告的确定性投影。
